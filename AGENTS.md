# Project operating notes

- The Supabase project used by this site is **shared with other websites**.
- Database work must be additive and scoped to the `megcredit_` prefix.
- Never delete, truncate, rename, alter, or reuse unrelated Supabase objects or data.
- Never expose `SUPABASE_SERVICE_ROLE_KEY` in browser code or in variables prefixed with `VITE_`.
- Contact submissions belong only in `public.megcredit_contact_submissions`.
- Client portal data belongs only in `public.megcredit_client_accounts`, `megcredit_client_invites`, `megcredit_client_sessions`, `megcredit_client_documents`, `megcredit_portal_login_attempts`, and the private Storage bucket `megcredit-client-documents`.
- The portal does not use Supabase Auth (`auth.users` is shared infrastructure across tenants) -- it has its own app-level accounts/sessions. All access to portal tables goes through the service role from `/api/portal/*`; RLS stays enabled with no grants to `anon`/`authenticated`, same as the rest of this project.
- Never store a client's full SSN as text in the database. SSN verification is collected only as an uploaded document (`document_type = 'ssn_card'`).
- **Deliberate exception:** `megcredit_client_credit_monitoring` stores each client's credit-monitoring login (IdentityIQ/SmartCredit/etc.), which the client explicitly submits so staff can pull their reports -- this is a conscious, informed business decision (confirmed twice after the security tradeoffs were explained), not an oversight of the "no third-party credentials" rule above. `password_encrypted`/`security_word_encrypted` are encrypted at the application layer with AES-256-GCM (`api/_lib/crypto.js`, key in `PORTAL_CREDENTIAL_ENCRYPTION_KEY`) before being written, so a raw database read doesn't expose plaintext. Only `api/admin/client-credit-monitoring.js` decrypts them, and only for an authenticated staff session -- never include decrypted values in `api/admin/client-detail.js` or any other broader response.
- Admin/billing data belongs only in `public.megcredit_staff_accounts`, `megcredit_staff_sessions`, `megcredit_service_catalog`, `megcredit_payment_plans`, `megcredit_client_services`, `megcredit_service_agreements`, and `megcredit_stripe_webhook_events`. Same rules as above: additive, RLS enabled, no grants to `anon`/`authenticated`, service role only from `/api/admin/*` and `/api/portal/*`.
- Credit bureau data (Equifax/Experian/TransUnion scores + dispute status shown on the client portal) belongs only in `public.megcredit_client_bureau_links`, `megcredit_client_bureau_reports`, `megcredit_client_bureau_scores`, `megcredit_client_bureau_case_status`, and the private Storage bucket `megcredit-bureau-reports`. Same rules as above. Two sources feed the same shape: a ConsumerDirect Partner API sync (`source = 'api'`, only for clients enrolled under MEG Credit's sponsor code -- see `megcredit_client_bureau_links`) and staff-uploaded 3-bureau PDFs (`source = 'pdf_upload'`) for clients who were not. PDF-parsed data is never shown on the client portal until a staff member reviews and confirms it (`parse_status = 'confirmed'`) via `api/admin/bureau-report-confirm.js` -- automated PDF parsing (`api/admin/bureau-report-parse.js`) is best-effort only.
- ConsumerDirect/SmartCredit API calls (`api/_lib/consumerdirect.js`, used by `api/admin/bureau-link.js` and `api/admin/bureau-sync.js`) go through `undici`'s `ProxyAgent` as the `fetch` `dispatcher`, pointed at a self-hosted static-IP proxy (`CONSUMERDIRECT_PROXY_URL`) -- ConsumerDirect requires calls to originate from a static, dedicated, US IP, which Vercel functions don't have on their own. `api/admin/bureau-sync.js` stores the raw `/v1/credit/3bs/current` response in `megcredit_client_bureau_reports.raw_payload` and sets `parse_status = 'needs_review'` rather than auto-mapping fields into scores/case status, since the real JSON shape hasn't been verified against a live response yet -- staff fills in the values by hand from `raw_payload`, same review/confirm flow as `pdf_upload`.
- Staff accounts are a separate table/session/cookie from client accounts on purpose -- a bug in client auth must never be able to escalate to staff access. The only way to create a staff account is `POST /api/admin/bootstrap-staff` with `PORTAL_ADMIN_TOKEN` (no self-serve staff invite UI).
- Stripe is integrated by direct REST calls with `STRIPE_SECRET_KEY` (`api/_lib/stripe.js`), not the `stripe` npm package, consistent with how this project calls Supabase/Resend. `api/stripe-webhook.js` verifies the `Stripe-Signature` header itself (HMAC-SHA256 over the raw body) and is the one endpoint that doesn't check `allowedOrigin`, since Stripe -- not a browser -- calls it. Never expose `STRIPE_SECRET_KEY` or `STRIPE_WEBHOOK_SECRET` to the browser.
- Blog content has two independent sources that must not be merged: `megcredit_blog_posts` is hand-authored, block-based content (see `src/data/posts.jsx`) rendered at `/blog/:slug`. `megcredit_indexal_articles` is delivered by the Indexal (getindexal.com) publishing webhook (`api/indexal-webhook.js`, verified via `INDEXAL_WEBHOOK_SECRET`/`api/_lib/indexal.js`) and carries full HTML per Indexal's own schema (author, CTA, hero/infographic images, per-language deliveries linked by `translation_group_id`). Indexal articles render at `/blog/:slug` for `es` and `/en/blog/:slug` for `en` (`src/components/IndexalArticle.jsx`, sanitized with `isomorphic-dompurify` since the HTML comes from a third-party service). A successful webhook delivery fires `VERCEL_DEPLOY_HOOK_URL` to trigger a full rebuild -- `scripts/generate-seo-files.mjs` (part of `npm run build`) regenerates `public/sitemap.xml` and `public/llms.txt` from both blog sources plus the static routes on every build, so they always reflect the latest published articles in both languages.
